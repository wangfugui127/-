# 商城边界修复验收（2026-10-11）

本次修改仅限 Java 商城，保留原订单、库存、Outbox、签名回调和退款补偿机制。

## 已修复

1. **支付失败可重试。** 同一待付款、未过期订单可在 FAILED 后创建新尝试；每次保存独立支付号、请求键及消息。同键重放原尝试，不同新键遇到 CREATED 返回 PAYMENT_IN_PROGRESS；旧回调和旧 Outbox 消息仅处理原记录。订单详情展示最新支付。前端失败后可重新支付，刷新后仍可用；响应丢失时保留请求键，服务端订单详情确认相同请求后清除。普通订单和秒杀订单均验证，不重复扣库存，不重新占用秒杀资格。
2. **待付款订单上限为 20。** 普通直接下单、购物车下单和秒杀下单取得同一用户的独立 order_creation_lock 行锁，在任何一致性快照读取前串行化；锁内先重查幂等请求，再 COUNT 待付款总数。已满时重复原请求仍返回原订单。独立锁避免用户表独占锁与购物车外键检查产生环路。
3. **旧查询不能跨失效回填缓存。** 失效消费者用 Lua 原子递增代次并删除缓存，查询在 DB 读取前捕获代次，回填时同时检查代次与加载锁所有者。正缓存和空值缓存均受保护，Redis 故障时不回填。代次键保留，避免 TTL 归零后接受过时结果。

- Java 21.0.12.1，`mvn -q verify`：**33 项通过**（6 单测 + 27 真实 MySQL/Redis 集成场景），失败/错误/跳过均为 0。
- 新增场景：普通/秒杀失败支付重试、同键并发重试、旧回调隔离、最后一个待付款名额的跨商品并发、普通/秒杀竞争同一名额、购物车外键锁兼容、DB 查询完成后失效再回填。
- 前端 `npm run build`、`npm run lint` 通过；**9 项单测通过**，含响应丢失后的支付确认与新键生成。
- Docker 前端 `http://127.0.0.1:8088`：**7 项 Playwright 验收通过**，包含完整购买/发货/收货、购物车、活动资格及两类失败支付重试。
- 运行中的数据库从 V2 升至 V4：V3 改支付唯一索引，V4 增加独立下单锁；保留现有数据。迁移先创建组合索引再删除旧索引，持续满足支付表外键所需索引。
- 已更新 Docker 后端/前端并确认健康。迁移后英文构建入口使用 `F:/app/workspaces/minimall-java`，指向新项目目录。

## 验证边界

支付渠道仍为模拟，不涉及真实资金；缓存异步失效消息到达前仍可能短暂陈旧，当前修复消除失效之后旧查询再次填入的竞态。并发测试覆盖上述受控场景，不作为生产吞吐量证明。可靠支付网络重试应传 Idempotency-Key；未传键的兼容接口不能识别客户端是否在重放同一失败尝试。
